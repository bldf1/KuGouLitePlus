# 测试与验证方法

本项目的绝大部分结论都来自真机验证。这份文档说明**判据是什么、为什么可信、以及怎么复现** ——
因为在这个项目里，"看起来没问题"和"验过没问题"差距很大（见文末的两个反例）。

---

## 一、三条核心判据

### 1. 真闪现判据：`严格=是`

日志里每条隐藏动作都带两个字段：

```
UI净化[某规则] 隐藏: <控件类名> v=<hash> 已绘制=<是|否> 严格=<是|否> <宽>x<高>
```

- `已绘制`：该视图在**本次挂载之后**是否已经被绘制过
- `严格`：在其基础上再要求 `宽>0 且 高>0`

**判据用 `严格`，不能用 `已绘制`。** 原因：`已绘制` 对 0×0 视图大量假阳性
（宿主控件重写 `onAttachedToWindow` 却不调 super 时，`wasDrawn()` 会把上一次生命残留的
`drawingTime` 误判成本次已绘制）。

**含义**：`严格=是` 表示"我们把它隐藏时，它已经**真的画到屏幕上**了" = 用户看到它闪了一下。
零闪现的目标就是让所有隐藏动作都发生在 `严格=否`（尺寸还是 0）的时刻。

> ⚠️ **判据边界（重要）**：模块对已隐藏的视图会**同时置 `alpha=0`**（"alpha 保险"，
> 防止宿主把已隐藏的视图复活后画出来）。而 `alpha=0` **不阻止 `onDraw`** ⇒ 视图照样"已绘制"，
> 只是像素全透明 ⇒ 此时 `严格=是` **不再等于"用户看得见"**。判断有没有真闪要看日志里的
> `alpha` 字段：`alpha=0.0` 即为不可见（本项目自带工具已按此过滤）。

### 2. 顶栏背景判据：自参照均匀度

顶栏背景是**渐变**，所以不能用固定参考色。做法：取顶栏区域一条带（y 110–250），
以该带**中位色**为基准，统计"接近中位色"的像素占比：

| 状态 | 均匀度 |
|---|---|
| 正常 | **90% ~ 96%** |
| 原生（模块全关）参考 | 约 94% |
| **异常**（顶栏背景/蒙罩消失，内容裸顶） | **0%** |

阈值取 0.70。这是**唯一**能抓到"顶栏背景消失"这类问题的自动判据 ——
它根本不是隐藏事件，`严格=是` 抓不到。

### 3. 底栏判据：胶囊下方带均匀度（**语义与顶栏相反**）

取胶囊下缘以下的那条带（y 2656–2706），同样算自参照均匀度：

| 状态 | 均匀度 | 含义 |
|---|---|---|
| **原生**（模块全关） | **100%** | 原生底栏给内容留了 paddingBottom，内容铺不到胶囊下方，那块是纯宿主浅底 |
| **本模块生效** | **0% ~ 75%** | 内容铺到了胶囊下方（这是设计目标） |

⇒ **报警方向是"均匀度 ≥ 0.90"**（退回原生平底 = 相关修复被撤销）。只在**中途滚动位置**测，
滚到列表真末尾时该带本来就会变平。

## 二、回归怎么跑

### 单开关矩阵
**每次只关一个开关**（其余保持默认开）→ 冷启动 → 上滑若干次 → 检查上面三条 + 应用级异常。
"只关一个"是关键：模块其余部分仍在工作，任何回归都会暴露出来。

⚠️ 已知假阳性（必须排除，否则每次都会误报）：
- `W WindowManager: Exception thrown during dispatchAppVisibility` —— 系统进程的常规告警，不是崩溃
- 关掉「悬浮底栏」时，胶囊下方带 100% 是**正确**的（本来就要恢复原生平底）

### 全场景走查（多轮）
冷启动 → 依次走 发现页 / 我的页 / 乐库 / 搜索页 / 播放页 / 下拉频道 / 设置面板，
每步**增量拉取日志并清空**（模块日志有行数上限，长扫描会翻滚丢证据），统计 `严格=是`。

## 三、⚠️ 两个真实反例（为什么不能只看结论数字）

### 反例 1：工具没覆盖到，"0 条"毫无意义
全场景走查里的"播放页"步骤，原先只发一次点击就往下走，**经常并没有真正打开播放页**
（比如搜索浮层没退干净时那一击被吃掉）。结果是：**播放页的所有规则整轮都没被执行**，
报出来的"0 条闪现"是**假阴性** —— 而真实存在的闪现被漏掉了好几轮。

**修正做法**：点完**必须验证**（用 `dumpsys` 确认层级里出现播放页特征节点：书签槽位
`dt7`/`elq`，即便被隐藏节点仍在；或广告蒙层类名），没打开就重试，并在汇总里
**如实标注每轮到底有没有打开**。

> ⭐ 结论：**任何"0 条"都要先说清"这一轮到底执行了哪些场景"。**

### 反例 2：凭"类名/症状"猜，会把真目标一起废掉
某个规则出现了"隐藏发生在已绘制之后"的日志，当时判断是"它误伤了另一个页面里同类的控件"，
于是按**类名**把那个类排除掉。结果：**该类正是真目标的类** ⇒ 功能被整个废掉，
用户实锤"该隐藏的又出现了"。

**修正做法**：先 dump，比较两处的**祖先链**。真机上确实存在"**同类同 ID、只有祖先链不同**"的情况
（例如两处控件都是同一个类、同一个 id，但一处在 `TwoViewSwitchLayout` 下、另一处不在）。

> ⭐ 结论：**下门禁前先 dump 祖先链，别凭"类名/症状"猜。**

## 四、怎么确认"改热路径没有性能代价"

本模块会 hook 若干高频方法（`setVisibility`、`addView`、`addViewInLayout`、
`attachViewToParent`、`setText` 等）。改动这些路径**必须实测**，不能凭感觉：

1. `adb shell dumpsys gfxinfo <包名> reset` 清零统计
2. 走一段重负载（例如连续 20 次上滑，触发大量列表复用）
3. `adb shell dumpsys gfxinfo <包名>` 读结果

参考量级（本机 1220×2712 / 120Hz，重负载滚动）：

| 指标 | 可接受 |
|---|---|
| `Janky frames` | **0%**（曾出现过 8.7% 的劣化版本） |
| 90 / 95 / 99 分位 | 9 / 9 / 11 ms（曾出现过 90 分位 44ms 的劣化版本） |
| `Missed Vsync` / `Slow UI thread` | 0 |

## 五、设备与环境

- 测试机：小米 22081212C / Android 16 / HyperOS / 1220×2712 / dpi 3.0 / 120Hz
- 宿主：酷狗概念版 `com.kugou.android.lite` v5.2.9
- 框架：LSPosed（libxposed API 102）

⚠️ 做"原生对照"**不要卸载模块 APK** —— LSPosed 会记 `Failed to find package info`，
重装也不恢复，必须重启手机。正确做法是把所有开关写为关闭（hook 仍在但规则不触发），效果等价且零风险。
